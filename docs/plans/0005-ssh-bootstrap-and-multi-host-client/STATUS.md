# Plan 0005 — SSH Bootstrap and Multi-Host Client — 🚧 In progress

The roll-up row in [../STATUS.md](../STATUS.md) must stay in sync with this file. Task-level truth lives in [tasks/](tasks/) frontmatter; Makina's integration coordinator updates both layers.

- **Status:** 🚧 In progress.

- **Goal:** connect the client engine to remote hosts over the user's own SSH configuration, bootstrap the server and terminfo where they are missing with an explicit upgrade policy, and hold several hosts concurrently behind a client-side model with optimistic commands — proven end to end from a bare engine container against two hosts through link drops.
- **Root cause:** the daemon speaks only to its relay, there is no client-side model in front of it, and multi-host identity cannot be retrofitted after a single-host model has shipped.
- **Approach:** shell out to `ssh` with `ControlMaster` so `~/.ssh/config` keeps working unchanged; probe, upload, verify, launch and never again, each stage driven from the engine container by a step of its own; never replace a daemon silently; key everything on global identity so a pane survives a host reconnect and the client resumes rather than rebuilds; and make every interval a field so a link-drop proof takes seconds.
- **Progress:** 6/13 tasks done; 0 blocked; 0 dropped.
- **Integration:** `planned`; run —; base `develop`; validation base —; mode —; final integration —.
- **Exceptions:** `ssh-control-master` records two. `SshTransport::arguments` is public beyond the architecture's list, because what the vector *lacks* is the property this task exists to hold — every option a person could have written in their own configuration — and asserting an absence needs the value, not a process. `SshTransport::spawn` and `close_master` are not `async`, though the architecture writes `spawn` that way: neither awaits anything, since `tokio::process::Command::spawn` is synchronous and what a caller waits for is the child — and clippy's `unused_async`, which this workspace denies, refuses an `async fn` with nothing to await. The signature the architecture asks for cannot be written under the lint set the same document requires. And `classify` takes the host as well as the status and the words, because every variant of `SshError` carries which host it is about and a classifier that did not know would have to be told twice.

  Its `HostKeyChanged` says "the host key was not accepted" rather than "is not the one remembered", because `ssh` prints `Host key verification failed.` both for a key that changed and for one that was never known under strict checking. The architecture's variants are fixed and both are the host's key rather than the network; the detail carried is the line that matched — its review's doing, recorded below — which says which it was, and the alarming sentence is conditioned on the first.
  Its review found ten, and the first was user-facing. `classify` read `ssh`'s words before its exit status, so a remote binary without its executable bit — which exits 126 saying "Permission denied" — was reported as the host refusing the credentials, and a person was sent to look at their keys for a file mode. The status decides first now: 255 or none is `ssh`'s own failure and the words say which, and any other status is the command's, with what it exited with and what it said. The detail carried is the line that matched rather than the last line, because `ssh` ends both host-key failures with the same generic sentence and a first connection to an unknown host would otherwise read exactly like a key that changed under someone.

  Three more were about time. `ssh` takes whole seconds and a zero is not "at once" but "never" — `ControlPersist=0` keeps a master for ever — so a field under a second is rounded up rather than truncated into its opposite. The transport step ignored its own deadline, which mattered because it is the one step kind that opens a network connection and so the one that can stall after the connect where `ConnectTimeout` no longer applies; it has one now, and it is what constructs `SshError::Timeout`. And the unreachable scenario asserted only that the step failed, not that it failed inside the two seconds it was given, which is what its claim says.

  The rest: the runtime directory is refused unless it is a real directory this user owns, because the fallback is a predictable name in a shared temporary directory and `create_dir_all` follows a link — someone who planted one first would have had this restrict a directory of their choosing and then fill it with live SSH connections. The purity assertion matched short flags as substrings of the whole command line, so a `TMPDIR` containing `-i` would have failed it for nothing. And the module says, on the record, that three of the six options iznik owns are ones a person may also have written and that a command line beats their configuration.

  `remote-channel` records three. Its `RemoteChannel` holds the `SshChild` for its own life rather than only the pipes it took from it: the transport spawns with `kill_on_drop`, so letting the child go after taking its standard streams kills the very process those pipes lead to — which reads, from the other end, exactly like a host that closed the link, and did.

  Its step's vocabulary is the client step's narrowed rather than repeated. There is no `hello`, because opening a channel *is* the handshake, and nothing about reassembly, because that belongs to the step that has an oracle. What it gains instead is `pause_server`, and the reason is the driver's shape: every step is its own process, so a channel opened in one is gone by the next and a network fault between them would be met by the *opening* of a second channel rather than by the silence of the first. The step stops the daemon itself through the same alias — the relay stays up, the socket stays open, and nothing answers — which is the link this task is about, inside one step where it can be watched.

  And the wait drains before it judges: whatever was in flight when the server stopped is still coming, and delivering it is the channel doing its job. What is asserted is what happens when there is nothing left.

  Its review found twelve, and the first was a claim that was false about its own proof: it said the host's network was cut, and the scenario stops the daemon. The claim says what is done now, and the reason is recorded with it — the fixture applies a fault between steps, a channel cannot outlive the process that opened it, and neither container carries the traffic tooling to cut a network from inside one, so a stopped daemon over a healthy link is the same silence from the channel's side, which is the side this task is about. The rest of that Test — a network fault and a channel opened after it is cleared — is what `integration-harness`'s `reconnect-over-ssh` already proves one layer down.

  Three were bugs a caller would meet. `next` took its deadline as a race against the reader, and a reader with a frame always ready wins it every time — so a wait for something a flooding pane never says had no bound at all; the deadline is checked before each poll now. The ping held the shared writer across its send, which parks when the peer has stopped reading: exactly the moment the ping fires, so the lock was held for ever and every caller that wrote wedged instead of being told the link was dead. It never waits for the writer now, because a writer something else is using says as much as a pong. And the step's per-action patience was `timeout.min(DEFAULT_PATIENCE.max(timeout))`, which is `timeout` — the twenty seconds it documented never applied.

  Two were silence where there should have been words. The `ssh` child's standard error was piped and never read, so a host with no server at the path it was given closed the link and the channel could only say that it had closed, while `command not found` sat unread in a pipe — and a long session would have filled that pipe and stopped the remote process in a write. It is drained into a bounded tail now and carried in the error. And `await_bytes` with an empty needle called `windows(0)`, which panics.

  Two were proofs that proved less than they said. `bytes-over-ssh` waited for the words it had typed, which a pseudoterminal echoes back before the shell runs — it waits for what the shell computes now. And two items on the task's Tests list had no case at all: a pane's bytes arriving as the pane's own, and compression engaged when the server offers it and not when it does not. Both are there.

  The rest: `resume_server` could never be reached, because the wait for death returns from inside itself, so the step undoes its own pause on the way out and the scenario no longer re-types the shell that finds the lock; `Deadline` measured its wait from the last frame heard rather than from the call; a ping interval of zero would have been a loop with nothing in it; and the scenarios were folded into a group of four while each takes three threads, which serialized thirty of them against a gate that calls fifteen minutes a hang — the group is twelve.

  `host-probe` records two. `probe` takes something that runs one command rather than a `Transport` itself — a `RunsRemotely` the transport implements — because "the probe is one round trip" is the point of the whole design and a count is the only thing that proves it. The trait has one implementation in the product and one in the test that counts.

  And the script creates nothing. Writability is answered by walking up to the first ancestor that exists and asking about that, rather than by making the directory and seeing whether it worked: a probe that changed the host before deciding whether to would have made three directories on every host it looked at, two of which it would never use.

  `terminfo-asset` records two. One field of the committed entry is not `infocmp`'s: its names were `xterm-ghostty|ghostty|Ghostty`, and `tic` warns that a last field with no blank in it may be read as a third alias by older versions rather than as the description. The task asks for a compile with no warnings, so the description is `Ghostty terminal emulator`, which is what ncurses asks for; the module header says so.

  And `iznik-client` gained `iznik-harness` as a development dependency, for its bounded process runner alone — the asset is proven by running the same `tic` and `infocmp` a host would, and section 8 says no spawned process runs without a deadline.

  `host-probe`'s review found twelve, and the first was a bootstrap that would have failed on a host it had itself provisioned. The script found a server by walking every candidate while `parse` chose a prefix by writability, and the two were independent — so a host where iznik had installed under the home's share, probed later from a session with a writable `XDG_DATA_HOME`, reported a server *and* a prefix that had none, and the launch would have opened a path that does not exist. Each candidate answers for itself now: where it is, whether this user may write it, and what an iznik server *there* says it is.

  Two were about a host nobody controls. The third candidate lives under `/tmp` when there is no `XDG_RUNTIME_DIR`, and `/tmp` is world-writable, so the walk up to it always answered yes — and the script then *ran* a binary found there. Another local user could have left one. A candidate that exists must now belong to this user, and so must a server before its version is asked for. And every variable is read with a default, because a host whose `~/.bashrc` sets `-u` turned every probe into a failed command rather than an answer — `dash -u` on the old script aborts at the first bare `$XDG_DATA_HOME`.

  Two were disagreements with the rest of the system. The runtime candidate appended a component the server's own `RuntimePaths::resolve` does not, so the place the probe would have installed to was not the place the daemon would look; and the terminfo check searched ncurses' default path rather than where `payload-upload` compiles the entry, which would have made `terminfo_installed` false on every host iznik had ever provisioned and re-run `tic` on every bootstrap.

  The rest: a version line was read without checking it began `iznik-server`, so anything at that path saying `something 9.9.9 protocol 1` was taken for one; a `--version` printing more than a line could append fields to the probe's own answer, including further candidates; a missing `tic` or `terminfo` line was read as "no" rather than as an answer that had gone wrong; two of the three candidates in the test fixture were the same string, which made the ordering assertion vacuous and the claim's "all eight ways they combine" untrue — it is eight now, over three distinct places; the round-trip claim said spawns and the test counts what the probe asked for, so it says that; and `DIRECTORY_NAME` had no consumer.

  `payload-upload` records one, and it is the scenario's. The upload that is cut short is driven by a writer that holds the pipe open after its half — a writer that closed it would give the script an end of input, and the rename would happen, which is the opposite of the case being made.

  `payload-upload`'s review found fifteen, and the first three were the script's. It swept every `.partial-` file before writing its own, so a second bootstrap of the same host — two windows, a retry, one machine under two aliases — deleted the file the first was still filling; only partials older than an hour are swept now, and the name comes from `mktemp` rather than from a process id that can be reused. The digest check did not fail closed: `got=$(shasum … | cut …)` is a pipeline, so a host with no `shasum` gave an empty digest with a zero status and nothing asserted one had been computed — a host with neither program is now told so and refuses, and an empty digest is refused with it. And `mkdir -p` never re-checked what it had made, so the `/tmp` hole the previous review closed was closed only for a directory that already existed at probe time: between the probe and the upload another local user could create `/tmp/iznik-<uid>/bin` and own what landed in it. The prefix and its `bin` must both be directories this user owns and neither may be a symbolic link.

  Those are properties of a shell and a filesystem, so they are proven against one: `crates/iznik-client/tests/upload_script.rs` runs `REMOTE_UPLOAD_SCRIPT` itself — installs what matches, refuses what does not and says which digest it computed, keeps a partial another run is filling and sweeps one nothing is, refuses a prefix reached through a link, and refuses a host with no way to take a `SHA-256`. The two container scenarios that used to retype a shortened copy of the script now put the constant on the host and run *that*, through the step's new `emit`: what they proved before could have stayed green after the real script lost its digest check outright.

  Two were about a bootstrap that failed for a reason that was not the reason. A `tic` that fails propagated out of `upload` and undid an install that had already succeeded, contradicting the module's own rule that a host without `tic` gets the server and no terminfo; a refusal now costs the terminfo, not the connection, and why it was refused is carried back rather than logged. And `terminfo_installed` — the field the probe's `TERMINFO_DIRS` fix exists to answer — had no consumer at all; it is what saves a host that cannot compile an entry today but has one from a day it could.

  Two were parsing. `candidate <path> <writable> <version>` was split on its first space, so a prefix containing one — `XDG_DATA_HOME` is whatever somebody set it to — read as unwritable and the probe refused the host with a reason that was not the reason; a candidate is three labelled lines now, each value the whole rest of its line. And the refusal's own words said "cannot be written by this user" where the test is ownership as well, which sends a person to look at permission bits.

  The rest: the headline fix of the commit before — the server read from the prefix that was chosen — had no case, and now has one that fails without it; exit sixty-five was read as a digest mismatch whatever produced it, with the digest taken from the last word of standard error, so a `mv` that failed the same way reported "the host received <garbage>", and the mapping is gated on the line that actually carries a digest; the artifact was read with `std::fs` inside an `async fn` and read twice, so what the host was told to expect need not have been a digest of what it was sent — it is `tokio::fs` now, and bytes that changed under it are refused naming both digests; `sync` flushed every mounted filesystem on the host where an `fsync` of one file was wanted; the terminfo source was a fixed name that two runs would interleave and a failed `tic` would leave behind for ever; and `installs-twice` counted the files beside the binary with a plain `ls`, which hides exactly the dotfiles the claim is about.

  One of its findings is recorded rather than acted on. The blocking policy covers `std::io`, `std::thread` and `std::process` in the two asynchronous crates and not `std::fs`, so nothing would have caught the read that was fixed. Widening it to `std::fs` would need an exception list of six files — the runtime directories both sides make at startup, the daemon's lock, a working directory checked before a pane is spawned — none of which is in an `async fn` and each of which would weaken the rule by being listed under it. The hazard is `std::fs` *inside* an `async fn`, which is a syntax-aware check and a change to plan 0001's gate that this plan does not authorize. It is written down here so the next person to touch that policy knows what it is for.

  `remote-launch` records four. `upgrade` and `uninstall` take a `BootstrapOptions` the architecture's parameter lists do not show, because both run a probe, a channel and — for one of them — an upload, and section 8 says every timing is a field somebody can shorten; without it a container scenario could not bound them.

  The whole budget is spent stage by stage rather than as one timeout around everything: each stage is given the lesser of its own deadline and what remains, so a bootstrap that runs out fails *as* a stage and the error says which. One outer timeout would have said only that six minutes passed.

  `uninstall` removes what iznik installed and then the prefix, when the prefix is empty. It does not delete the prefix outright, because one of the three candidates the probe offers is `XDG_RUNTIME_DIR` itself: a host that chose it would have had its whole runtime directory swept away by a command whose stated purpose is to leave the machine as it found it. Everything iznik put there goes; a directory iznik made goes with it; a directory it was lent does not.

  And `decide` is a public function of the probe's answer and the artifacts on this machine, taking no transport at all. That is what makes "a machine this build carries no artifact for is refused before anything is uploaded" a property a test can hold rather than a sentence a comment makes.

- **Outcome:** Several remote hosts held at once over ordinary SSH, each bootstrapped automatically from a machine that had nothing, each surviving link drops without losing pane identity or bytes, with unambiguous commands applying instantly and reconciling against the server.
